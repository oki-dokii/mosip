## Historical Collab nonce probe and new pinned local result

On 2026-10-21, synthetic mock X.509 issuer → Reference Wallet → public Collab Inji Verify generated a **new** SD-JWT presentation with a nonce different from the signed request. Verify's direct-post endpoint returned HTTP 400 with `invalid_request`, and no result was available. The playground's status poll then marked the run `errored` rather than a matched `invalid`. See [sanitized report](../submission/evidence/2026-10-21-nonce-mismatch.json), run `f8756c3d-1389-4196-85d8-8b1e2909cc1a`.

That Collab observation did **not** reproduce acceptance of a wrong nonce and was not a genuine byte-for-byte replay. The early-rejection handling was a **local harness gap at this historical run**; the merged BFF now records direct-post HTTP 400 without polling for a status that will never appear. The old report remains historical evidence and was not rewritten.

The separate [local 0.18.2 seven-case matrix](../submission/evidence/2026-10-25-local-inji-extended-matrix.json) now reproduces the opposite nonce behavior for its pinned configuration: three holder-binding/replay negatives returned `valid` and a signature-corruption control returned `invalid`. Every presentation used a fresh signed request; the replay case reused the exact previously accepted VP bytes with a new `state` and challenge. The probe locally verifies each holder signature and records boolean nonce/audience comparisons without logging either value. A wrong-state submission returned HTTP 404, while a descriptor path pointing outside the VP array still returned `valid`. The contradictory Collab and local outcomes must remain separate until the Collab build and profile are known. The probe intentionally exits nonzero on an accepted negative; this is a detected conformance failure, not a broken setup.

## External ecosystem protocol assessment: walt.id v2 vs Inji — 25 October 2026

Following the gating criteria (*"Add one independently implemented external issuer or verifier profile only if protocol versions align"*), Person 3 and Person 4 evaluated **walt.id Identity toolkit v2 (`Issuer2` / `Verifier2`, release `v1.2.0`)** against the pinned MOSIP Inji stack (`inji-certify v0.14.0`, `inji-verify v0.18.2`).

1. **Protocol Specifications Divergence:**
   - **OpenID4VCI:** walt.id `Issuer2` implements final OpenID4VCI 1.0 (Draft 14+ / Final), enforcing `credential_configurations_supported` metadata, batch issuance schemas, and mandatory PAR. Inji Certify implements Draft 13 with `credential_definitions` and draft-era endpoints.
   - **OpenID4VP Query:** walt.id `Verifier2` enforces Digital Credentials Query Language (DCQL) and compact signed Request Objects. Inji Verify and Inji Wallet strictly require DIF Presentation Exchange 2.0 (`presentation_definition`).
   - **Response Mode & Encryption:** walt.id `Verifier2` enforces encrypted response mode (`direct_post.jwt` via JWE). Inji Verify does not support response decryption, requiring cleartext `direct_post` with unencrypted JWS payloads.
   - **Trust Architecture:** walt.id relies on European EUDI / ETSI trust anchors and `x5c` leaf trust lists, whereas Inji Verify requires MOSIP Keymanager trust anchors.

2. **Stopping Rule Application:**
   Because automated cross-ecosystem interop cannot function without non-standard DCQL-to-PEX translation shims, JWE decryption bridges, and draft-13/14 protocol adapters, Person 3 invoked the project stopping rule:
   > *"Stop an exploratory track when it cannot produce a reviewable result before the working code freeze; mark it `not_implemented` or `not_tested`."*

3. **Status:**
   The October study left this cell untested. The November experiments below supersede that stopping decision.
