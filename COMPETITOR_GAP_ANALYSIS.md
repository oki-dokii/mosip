## What the snapshot actually establishes

The archive contains a pinned Compose stack for Certify 0.14.0, Verify 0.18.2, Mimoto 0.22.0, and Inji Web 0.17.0 (`deploy/inji-stack/compose.yaml`). It contains a `live-core` matrix with 16 cells and a `live-holder-web` matrix with 10 cells, each linked to a committed run record (`docs/interop-report/live/matrix.md`). **“26 as specified” includes 10 observed failures and one unsupported cell**; it does not mean 26 interoperable combinations. `TC_PG_WEB_03` records JSON-LD Certify → Inji Web → Verify as valid, while `TC_PG_WEB_04` records SD-JWT presentation failing. The repository also includes a browser test of Inji Web's own pages, 29 gap entries with issue drafts for public findings, a 123-cell reference matrix, and a one-command local-stack demo. Its `docs/STATUS.md` explicitly leaves phone-wallet testing, upstream issue filing, and full mDoc interoperability incomplete. We have not independently rerun its claimed 1,247 tests or live stack.

## Highest-yield experiments

1. **Local core:** Certify 0.14.0 → Reference Wallet → Verify 0.18.2 for SD-JWT and JSON-LD. Start with official upstream configuration, record every local change, and use synthetic identities. The other project's Compose is a compatibility reference, not a file to transplant. Its demo script says Docker needs at least 3.5 GiB and recommends about 6 GiB; check this machine's allocation before debugging slow startup.
2. **Local Inji Web:** add Mimoto/Web only after core health. Run the browser's login, receive, stored-card, and presentation steps. This may remove the Collab-account blocker, but it is not an A1 pass until our own verifier result and wallet evidence exist. Keep A2/mobile separately blocked until a real device result is recorded.
3. **Independent gap probes:** the nearest lead is their G16 (`x5c`-only SD-JWT verification) because our Collab `did:jwk` issuer failed while our X.509 issuer passed. Pin a local Verify version and change only issuer-key representation. For JSON-LD, test their G14 (Certify DID `assertionMethod`) with a standards-based verifier, and G22 (holder key mismatch) only after Mimoto is running. Their G25 (Web SD-JWT presentation) needs a pinned logged-in Web run. Do not claim any of these based on the archive.
4. **Correct the harness:** turn a direct-post HTTP 400 into a terminal `invalid` or `error` result with its stable reason, rather than polling forever. Create a signed-expired credential at issuance and a wrong-holder case that leaves the issuer proof valid. These improve the credibility of every negative cell.
5. **Judge-facing proof:** run a small browser smoke and accessibility check, commit an independently reproducible matrix and UI screenshots, then rehearse the documented startup on a fresh machine. The existing redaction pipeline and evidence tiers are our strongest distinction; show them in the demo.
