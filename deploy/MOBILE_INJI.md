# Android SD-JWT setup: official local Certify + Collab Verify

This is the implemented Person 4 path around the observed Collab `Client ID is invalid` blocker. It runs **official Inji Certify** locally with its embedded PKCS12 keymanager, built-in pre-authorized token service and built-in `PreAuthDataProviderPlugin`. It uses public Collab Inji Verify for presentation verification. This is a hybrid deployment; Collab's running Verify release remains `unreported`.

A local automated control must issue and verify successfully before the console creates a phone offer. That control uses an ephemeral Reference Wallet key and does not close A2. The actual Android wallet must still issue, store and present its own credential.

## Start

Prerequisites: Docker Desktop/Engine running, Node/pnpm from the root project, `openssl`, `tar`, outbound HTTPS and enough disk/RAM for the dedicated PostgreSQL and emulated Certify containers. On the current Apple Silicon Mac, Certify uses the upstream-supported `linux/amd64` emulation. Other platforms can supply a locally installed `cloudflared` with `MOBILE_TUNNEL_BIN`.

```sh
pnpm install --frozen-lockfile
pnpm mobile:inji
```

On macOS ARM64 the launcher can download the official Cloudflare client `2026.10.3` and verify its release archive SHA-256. The first start may take several minutes while images download and Java starts. The launcher stays running; closing it ends the phone's temporary HTTPS route. It does not stop unrelated projects or delete Docker images/volumes.

When ready, it prints:

```text
Reference Wallet control: official Certify issued; Collab Verify returned valid. This does not close A2.
Open the local phone console: http://127.0.0.1:8060
```

The console is Mac-local. The phone accesses the displayed HTTPS issuer through the QR; do not enter `localhost` on the phone and do not change its existing registry/eSignet settings.

## On the Mac and Android phone

1. Open `http://127.0.0.1:8060` on the Mac. Confirm the control status is `valid` and note the displayed issuer hostname.
2. Click **Create fresh issuance QR**. The offer expires after ten minutes and can be consumed once. The synthetic identity is generated by the local setup; no eSignet login, personal ID or OTP is needed.
3. On Inji Wallet, use **Home → + → Scan & Download Card** and scan from the Mac. Check that the issuer matches the console. Approve the trust prompt if shown.
4. Wait for **Playground SD-JWT Identity** to appear. Open it, close/reopen the wallet and confirm the same credential remains. If issuance fails, record the exact screen; do not mark storage observed.
5. On the Mac, click **Create fresh presentation QR**. On the phone use its OpenID4VP sharing scanner, scan the new request, select the stored credential, review the requested data and approve sharing.
6. Click **Read Verify result** on the Mac. `pending` is not acceptance; wait briefly and read again. A complete same-wallet chain plus `valid` is required for A2. If invalid/error, record the actual outcome.
7. Save reviewed screenshots and bounded result summaries. Do not share offer QR contents, bearer tokens, raw credentials or private keys. The runtime files are private and are not submission artifacts.

The QR console generates the request rather than relying on the portal catalog containing this exact credential type. The control verifies the issuer signature, holder binding and exact SD-JWT prefix hash before checking a real Verify result. It does not verify certificate-chain trust or authenticate the signed Verify request; the helper restricts the request/response origins and checks client ID/nonce. This existing request-authentication limitation is retained explicitly.

## What changed from the failed phone attempt

- The failed offer used public Collab mock Certify with **authorization code**; the release source defaults to OAuth client `wallet`, which that attempt's eSignet rejected.
- This setup configures a separate official Certify instance as its own token issuer and uses its supported **pre-authorized grant**. It does not alter/register a client on Collab, replace the Inji wallet, or reuse another client's confidential key.
- Token issuer, audience, JWKS and credential endpoint are explicitly aligned to the runtime's HTTPS origin. The local pre-authorized issuance is independently checked; the earlier Collab HTTP 401 is not treated as fixed.
- Certify provides a real signed `dc+sd-jwt`, X.509 issuer certificate header and mandatory holder confirmation. Holder proofs are restricted to EdDSA for this first mobile profile, matching the successful control and avoiding untested ES256 holder behavior in the alpha wallet.
- The missing catalog entry is handled through a supported credential-offer QR, so Mimoto/catalog onboarding is not required for this particular path. A1 Web-wallet onboarding remains separate work.

## Runtime isolation and stopping

Default runtime directory: `mosip-mobile-inji` under the OS temporary directory. It contains generated passwords, key stores, bootstrap configuration and private diagnostic logs. Files are owner-only. It is never copied into Git or the normal app images. `MOBILE_RUNTIME_DIR` can select another location outside the repository, or the ignored `.mobile-inji/` directory in this repository. Preserve this directory while using its dedicated database; losing its generated passwords/keys requires deliberate recovery rather than deleting unrelated data.

The dedicated Compose project is `mosip-mobile-a2`; the database has no host port, and Certify binds only `127.0.0.1:18090`. The public gateway forwards only metadata, offer retrieval, nonce, token and credential paths. Offer creation, console actions, runtime files, actuator/admin APIs and raw logs are not public routes. Console POST actions require loopback/Host/Origin checks and JSON content type. No request bodies or authorization headers are logged by the gateway.

Stop with a second terminal:

```sh
pnpm mobile:inji stop
```

This stops the dedicated services and, when the launcher is present, its tunnel. Keys/database are preserved. Ctrl+C stops the launcher/tunnel; the stop command also stops its Docker services. A new start receives a new temporary hostname, recreates Certify with matching issuer properties and reruns the control. Use freshly issued credentials and fresh presentation requests after an endpoint change.
